# 开发路线图与决策清单

> 状态：Draft  
> 原则：每个 Phase 必须通过验收门槛后再进入下一阶段。首个目标是验证玩法，不是提前建设完整开放世界基础设施。

## 推荐默认值

在没有进一步决策前，Vertical Slice 使用：

- 单名玩家；
- 单个 Discord Server；
- 同步回合制，每个玩家窗口 5–10 分钟；
- 6 个 NPC、6 个回合；
- TypeScript 模块化单体；
- SQLite；
- 一个 Discord Bot + Webhook NPC 身份；
- 每个 NPC 每回合最多一个主要动作；
- Agent 同时基于回合 Snapshot 规划，再统一结算；
- 模型不可用时使用 Utility Policy；
- 玩家可观察所有频道，但 NPC 感知仍由系统隔离。

这些是可逆决策，不阻碍未来改为多人、异步或图形客户端。

## Phase 0：设计基线

### 目标

冻结第一局可实现的规则边界，避免实现阶段继续扩大世界观和动作范围。

### 交付物

- 世界背景与开发者真相；
- 6 个 NPC 初始档案；
- 地点和频道映射；
- 核心资源；
- 6 回合外部事件；
- 动作集合；
- 生存路线和结局条件；
- 架构边界；
- JSON Schema 或 TypeScript 类型草案；
- 架构决策记录（ADR）。

### 验收门槛

- 每条生存路线都有机器可判断的前置条件；
- 每个秘密都有明确的初始持有者或可发现来源；
- 每个动作都能定义前置条件和结果事件；
- 没有依赖自然语言才能完成的世界状态修改；
- 能手工走完一局纸面模拟。

## Phase 1：确定性模拟内核

### 目标

在没有 Discord 和 LLM 的情况下完成一局。

### 交付物

- GameSession 和回合状态机；
- WorldState 和 Projection；
- Domain Event 日志；
- Action Validator / Resolver；
- Scenario Director；
- 规则 NPC 或脚本 Intent；
- CLI runner；
- 固定 seed；
- Replay runner。

### 验收门槛

- CLI 能完成 6 回合并产生结局；
- 所有资源变化可追溯；
- 非法动作不能修改世界；
- 相同 seed 和 Intent 产生相同 Projection hash；
- 至少覆盖修井、夜海、撤离和商队四种结局；
- Domain tests 全部通过。

## Phase 2：Discord 游戏外壳

### 目标

把确定性模拟映射到 Discord，不引入 Agent 复杂度。

### 交付物

- Bot 初始化和 session command；
- 频道与地点绑定；
- 风塔广播；
- 玩家回合窗口；
- Webhook NPC 渲染；
- 消息发送队列和去重；
- 暂停、恢复和结束；
- `#agent-debug` 日志；
- 固定脚本 NPC。

### 验收门槛

- 一名玩家可以在 Discord 完成整局；
- 重复 Gateway event 不会重复执行动作；
- Bot 重启后能恢复当前回合；
- Discord 消息删除或发送失败不会破坏 WorldState；
- 所有频道输出都来自已提交事件。

## Phase 3：NPC Agent

### 目标

使用独立人格、目标、认知和记忆替换固定脚本 NPC。

### 交付物

- NPC Profile；
- Perception / Visibility Policy；
- Memory Store 和检索；
- Relationship；
- Planner structured output；
- Dialogue；
- Reflection；
- Model Gateway；
- 调用预算和 fallback；
- Agent trace。

### 验收门槛

- NPC 不会读取隐藏事实；
- schema 无效输出可恢复；
- 模型不可用时仍能结束回合；
- 行为差异不仅体现在语言风格；
- 玩家欺骗或帮助 NPC 后，后续决策出现可解释变化；
- 单局模型调用不超过预算；
- 6 NPC 无人干预可运行完整 6 回合。

## Phase 4：可玩 Vertical Slice

### 目标

完成《阿萨拉：噬日风暴》的首个外部试玩版本。

### 交付物

- 完整 NPC 内容；
- 条件化主线事件；
- 线索和秘密传播；
- 结局叙事；
- Onboarding；
- 单局报告；
- 试玩问卷；
- 自动评估脚本；
- 成本和延迟报告。

### 验收门槛

至少完成 10 局内部测试和 5 局外部测试，并满足：

- 80% 以上的游戏可以正常结束；
- 非法世界状态为 0；
- 信息泄露问题为 0；
- 至少产生 3 类不同结局；
- 多数测试者可以从行为而非姓名辨认至少 4 个 NPC；
- 多数测试者认为自己的信息选择改变了局势；
- P95 单次 Agent 决策延迟和单局成本处于预设预算；
- 每个失败都能通过事件和 Agent trace 定位原因。

## Phase 5：玩法判断

Phase 4 后先判断是否值得扩张，而不是自动继续开发。

### 继续的必要条件

- NPC 自主行为本身产生可复述的故事；
- 玩家愿意重玩以观察不同结局；
- 玩家主要在做判断和关系管理，而不是等待 Agent 聊天；
- 调试和成本可控；
- 增加 NPC 或地点能够增加玩法，而不是只增加噪音。

### 如果验证成功

优先扩展：

1. 第二名玩家或多人阵营；
2. 更多可组合场景；
3. 长期关系与跨局记忆；
4. 异步世界时钟；
5. Web 可视化地图；
6. 图形客户端；
7. 更大规模 NPC LOD 调度。

## 当前需要继续讨论的产品决策

### D1：玩家定位

推荐：玩家是“风塔联络官”，有影响力但没有直接统治权。

待决定：

- 玩家是否拥有自己的物品和健康状态；
- 玩家是否可以亲自执行维修、救援等动作；
- 玩家是否能撒谎而不受系统限制；
- NPC 是否可能公开罢免、驱逐或攻击玩家。

### D2：游戏节奏

推荐：首版同步 6 回合，每个玩家窗口 5–10 分钟。

备选：

- 90 分钟连续完成；
- 每个现实日推进一个回合；
- NPC 在玩家离线期间继续运行。

首版不建议异步常驻世界，因为难以控制成本，也不利于重放和测试。

### D3：玩家可见范围

推荐：测试阶段允许玩家以观察者身份查看所有地点，但明确区分“玩家知道”和“NPC 知道”。

正式玩法可改成：

- 玩家每回合只能进入一个地点；
- 只能看到风塔收到的报告；
- 使用角色权限隐藏地点频道。

### D4：对话自由度

推荐：玩家可以自由输入，NPC 输出自由文本；世界动作必须结构化。

需要决定是否允许玩家通过自然语言提出系统未知的行动。首版建议 Bot 返回可用动作或将其解释为 `talk`，而不是让模型临时创造新规则。

### D5：主线确定性

推荐：外部威胁与开发者真相固定，NPC 行动和最终方案开放。

这样既能稳定测试，也能产生不同故事。首版不建议让模型临时改变哈曼是否存活、母井为何缺水等基础事实。

### D6：失败体验

需要决定失败是否：

- 立即结束；
- 继续到第六回合并生成灾难结局；
- 允许玩家在失败后查看所有 NPC 的秘密和因果链。

推荐继续模拟到结局，并在赛后报告中展示关键因果链。

## 建议的下一步

1. 审阅并确认 Phase 0 的世界规则；
2. 为 D1–D6 建立 ADR；
3. 定义 TypeScript domain types；
4. 定义 `ActionIntent`、`DomainEvent` 和 Scenario 配置 schema；
5. 制作一份不依赖模型的手工回合样例；
6. 通过后进入 Phase 1 实现。
